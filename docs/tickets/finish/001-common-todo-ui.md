# TASK-001: 共通ToDo UI

## 概要

全学習ページで同じ見た目と基本操作を使える、日本語の一画面ToDo UIを設計・実装する。Microsoft To Doの一覧性を参考にするが、デザインの完全な複製は行わない。

## 学習目的

レンダリング方式を変えても比較軸がぶれない共通UIと、データ処理に依存しないコンポーネント設計を理解する。

## 前提

なし。

## 対象URL

なし（後続チケットの各URLで利用する）。

## 主な対象ファイル

- `src/components/todo/` 配下の表示用コンポーネント
- `src/styles/` または既存のスタイル定義
- ToDo型を置く既存の型定義ファイル

## 実装内容

- [ ] `Todo`型（`id`、`title`、`completed`、`createdAt`）を定義する
- [ ] 「My Tasks」と現在日付を表示する
- [ ] 一覧上部に入力欄を置き、Enterで追加要求を発火できるようにする
- [ ] 完了・未完了、タイトル、削除操作を1行に表示する
- [ ] タイトル編集と完了済みの視覚表現を用意する
- [ ] 「すべて」「未完了」「完了」のフィルターを用意する
- [ ] 登録件数と未完了件数を表示する
- [ ] ローディングとエラーを表示できる領域を用意する
- [ ] デスクトップとスマートフォンで操作できるレスポンシブ表示にする
- [ ] `Rendering: ...`を表示できる小さなラベルを用意する

## 実装上のポイント

表示コンポーネントは、ToDo配列、状態、イベント通知をpropsで受け取れる形を基本とする。データ取得や保存を共通UI内へ固定すると、後続ページのCSR、SSR、Server Actionなどの違いが隠れるため、学習対象の処理は各ページ側に残す。現在日付は実行環境による差を意識し、hydration差異を起こさない表示方法を選ぶ。

このタスクではデータ取得、HTML生成、キャッシュ方式を決めない。ブラウザへ送るJavaScript量も利用側のServer/Client境界で変わる。

## AIへ実装を依頼する学習方針

このタスクでは、AIにコードを書かせることだけでなく、人が業務上の利用シーンと技術選定の意図を整理し、AIが実装へ反映しやすい指示として伝える練習も行う。AIへ依頼する前に、少なくとも「誰が・どの場面で使うか」「現在何に困っているか」「期待する操作と結果」「技術上・業務上の制約」「今回の対象外」「どの観測結果で完了とするか」を具体化する。

- [ ] AIへの依頼文に、利用者、利用シーン、解決したい問題を記載する
- [ ] 期待する入力、操作、出力、失敗時の挙動を記載する
- [ ] Server／Client Componentの境界、URL状態、通常関数など、比較すべき代替案を記載する
- [ ] パフォーマンス、アクセシビリティ、セキュリティ等、このタスクで守る制約を記載する
- [ ] 実装しない範囲と、過度な共通化・最適化を避ける条件を記載する
- [ ] DevTools、Profiler、ログ、テスト等による確認方法を依頼時点で記載する
- [ ] 情報が不足する場合、AIに重要な前提を明示または確認させ、暗黙の仮定で実装範囲を広げさせない
- [ ] AIが生成したコードについて、依頼内容のどの指示がどの実装判断へ反映されたかレビューする

ソースコードの学習メモは、APIの構文説明ではなく「利用シーンから実装判断へ至る過程」を後から追跡できる内容にする。該当する要所では、次の定型表現を使用する。

```text
学習メモ: 利用シーン - 誰がどの状況でこの処理を必要とするか
学習メモ: 指示の要点 - AIへ渡した要件・制約のうち実装へ影響した内容
学習メモ: 採用理由 - 代替案と比較して、この実装を選んだ理由
学習メモ: 不採用条件 - この方法を使うべきでない条件
学習メモ: 検証方法 - 意図どおり反映されたと判断する観測方法
```

すべての分類を全箇所へ機械的に記載する必要はない。設計境界、状態管理、データ取得、副作用、最適化、エラー処理など、判断理由がコードだけでは分かりにくい箇所へ必要な分類を選んで記載する。
## AIコーディング時のコメントルール

- [ ] AIにコード生成・修正を依頼する際は、学習上重要なソースコードへ日本語の解説コメントを付けるよう指示する
- [ ] 解説コメントの先頭には検索用の定型文字 `学習メモ:` を必ず記載する（例: `// 学習メモ: このコンポーネントはデータ取得方式に依存しない表示を担当する`）
- [ ] UIとデータ処理を分離する理由、propsの役割、後続タスクで再利用する境界をコメントで説明する
- [ ] コードを逐語的に言い換えるだけのコメントや、すべての行への過剰なコメントは避ける
- [ ] 実装完了後に `学習メモ:` を検索し、重要な設計判断へコメントが付いていることを確認する

## 確認方法

- [ ] 仮のToDoデータとイベント関数を渡して全状態を目視する
- [ ] キーボードだけで追加、編集、完了切替、削除へ到達できるか確認する
- [ ] Chrome DevToolsのデバイス表示で狭い画面でも横スクロールや重なりがないか確認する
- [ ] 完了済み、空一覧、ローディング、エラーの各状態を確認する

## 完了条件

- [ ] 指定された表示・操作要素が一画面に揃っている
- [ ] UIが特定の取得・更新方式へ依存していない
- [ ] 日本語UIと方式ラベルを表示できる
- [ ] デスクトップとスマートフォンで利用できる

## 学習後に説明できること

- [ ] UIを揃えることがレンダリング方式の比較に有効な理由
- [ ] 共通化すべき表示処理と、各学習ページに残すべき処理の境界
