# TASK-012: Server Action + Validation

## 概要

`/app-server-action-validation`のServer ActionにZodによる入力検証を追加する。

## 学習目的

クライアントから届く値を信頼せず、データ更新直前のサーバー境界で検証する必要性を理解する。

## 前提

TASK-011が完了し、Zodが未導入の場合は実装時に`bun add zod`で追加すること。

## 対象URL

`/app-server-action-validation`

## 主な対象ファイル

- `src/app/app-server-action-validation/page.tsx`
- `src/app/app-server-action-validation/actions.ts`
- 同ディレクトリのschema・componentsファイル

## 実装内容

- [ ] Zodでタイトルの空文字と空白のみを禁止する
- [ ] タイトルを最大100文字に制限する
- [ ] IDの形式と対象の存在を検証する
- [ ] 全更新Actionでサーバー側検証を必須にする
- [ ] フィールド単位のエラーを返して表示する
- [ ] 不正入力時に保存処理と再検証を実行しない
- [ ] `Rendering: App Router / Server Action + Validation`を表示する

## 実装上のポイント

HTML属性やクライアント検証は操作性向上には役立つが、改変・迂回できる。Server Actionの引数や`FormData`は信頼できない入力であり、Zodの`safeParse`等で保存前に検証する。業務上の「対象が存在しない」と形式エラーを区別する。

検証と保存はサーバーで動き、ブラウザへは必要なエラー情報だけをシリアライズして返す。TASK-011から成功経路は変えず、失敗を安全に扱う境界を追加する。

## AIへ実装を依頼する学習方針

このタスクでは、AIにコードを書かせることだけでなく、人が業務上の利用シーンと技術選定の意図を整理し、AIが実装へ反映しやすい指示として伝える練習も行う。AIへ依頼する前に、少なくとも「誰が・どの場面で使うか」「現在何に困っているか」「期待する操作と結果」「技術上・業務上の制約」「今回の対象外」「どの観測結果で完了とするか」を具体化する。

- [ ] AIへの依頼文に、利用者、利用シーン、解決したい問題を記載する
- [ ] 期待する入力、操作、出力、失敗時の挙動を記載する
- [ ] Server／Client Componentの境界、URL状態、通常関数など、比較すべき代替案を記載する
- [ ] パフォーマンス、アクセシビリティ、セキュリティ等、このタスクで守る制約を記載する
- [ ] 実装しない範囲と、過度な共通化・最適化を避ける条件を記載する
- [ ] DevTools、Profiler、ログ、テスト等による確認方法を依頼時点で記載する
- [ ] 情報が不足する場合、AIに重要な前提を明示または確認させ、暗黙の仮定で実装範囲を広げさせない
- [ ] AIが生成したコードについて、依頼内容のどの指示がどの実装判断へ反映されたかレビューする

ソースコードの学習メモは、APIの構文説明ではなく「利用シーンから実装判断へ至る過程」を後から追跡できる内容にする。該当する要所では、次の定型表現を使用する。

```text
学習メモ: 利用シーン - 誰がどの状況でこの処理を必要とするか
学習メモ: 指示の要点 - AIへ渡した要件・制約のうち実装へ影響した内容
学習メモ: 採用理由 - 代替案と比較して、この実装を選んだ理由
学習メモ: 不採用条件 - この方法を使うべきでない条件
学習メモ: 検証方法 - 意図どおり反映されたと判断する観測方法
```

すべての分類を全箇所へ機械的に記載する必要はない。設計境界、状態管理、データ取得、副作用、最適化、エラー処理など、判断理由がコードだけでは分かりにくい箇所へ必要な分類を選んで記載する。
## AIコーディング時のコメントルール

- [ ] AIにコード生成・修正を依頼する際は、学習上重要なソースコードへ日本語の解説コメントを付けるよう指示する
- [ ] 解説コメントの先頭には検索用の定型文字 `学習メモ:` を必ず記載する（例: `// 学習メモ: クライアントから届くFormDataは信頼せず、保存前にサーバーで検証する`）
- [ ] Zod schema、サーバー検証、検証失敗時に更新しない理由をコメントで説明する
- [ ] コードを逐語的に言い換えるだけのコメントや、すべての行への過剰なコメントは避ける
- [ ] 実装完了後に `学習メモ:` を検索し、Validation境界へコメントが付いていることを確認する

## 確認方法

- [ ] 空、空白、101文字、改変したIDを送信する
- [ ] DevToolsでクライアント制約を外してもサーバーが拒否することを確認する
- [ ] 拒否時に保存データが変化しないことを確認する
- [ ] サーバーログへ機密情報を含む入力全体を不用意に出していないことを確認する

## 完了条件

- [ ] 全不正入力がサーバーで拒否される
- [ ] フィールドエラーが対応する入力欄付近に表示される
- [ ] 不正入力でデータが更新されない

## 学習後に説明できること

- [ ] クライアント検証だけでは不十分な理由
- [ ] Zod schemaをServer Action境界で使う意味
- [ ] 形式エラーと業務エラーの違い
