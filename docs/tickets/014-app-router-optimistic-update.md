# TASK-014: Optimistic Update

## 概要

`/app-optimistic`で`useOptimistic`を利用し、サーバー応答前に操作結果を仮表示する。

## 学習目的

楽観的更新による体感速度の改善と、失敗時の復元・正式データとの整合性を理解する。

## 前提

TASK-013が完了していること。

## 対象URL

`/app-optimistic`

## 主な対象ファイル

- `src/app/app-optimistic/page.tsx`
- `src/app/app-optimistic/actions.ts`
- 同ディレクトリのClient Component群

## 実装内容

- [ ] `useOptimistic`で追加直後に仮ToDoを表示する
- [ ] 完了切替と削除を即時反映する
- [ ] Actionへ学習用の意図的な遅延を入れる
- [ ] 仮IDとpending中の見た目を区別する
- [ ] サーバー失敗時にエラーを表示し、正式データへ復元する
- [ ] 成功後にサーバー上の正式データと同期する
- [ ] `Rendering: App Router / Optimistic Update`を表示する

## 実装上のポイント

楽観stateとイベント処理はブラウザ、正式な検証・保存はサーバーで動く。成功を保証せず先に見せるため、同じ項目への連続操作、仮ID、順序、失敗時のrollbackを設計する必要がある。サーバーから再描画された正式データを唯一の確定情報として扱う。

TASK-013からAction結果を待つUIに仮状態を重ねる。キャッシュ再検証後に楽観stateが二重反映されないことを確認する。

## AIコーディング時のコメントルール

- [ ] AIにコード生成・修正を依頼する際は、学習上重要なソースコードへ日本語の解説コメントを付けるよう指示する
- [ ] 解説コメントの先頭には検索用の定型文字 `学習メモ:` を必ず記載する（例: `// 学習メモ: この状態はサーバー確定前の仮表示であり、失敗時には正式データへ戻す`）
- [ ] 楽観state、正式データ、仮ID、失敗時の復元をコメントで説明する
- [ ] コードを逐語的に言い換えるだけのコメントや、すべての行への過剰なコメントは避ける
- [ ] 実装完了後に `学習メモ:` を検索し、Optimistic Update固有の処理へコメントが付いていることを確認する

## 確認方法

- [ ] Networkを低速化し、応答前に追加・切替・削除が見えることを確認する
- [ ] Actionを意図的に失敗させ、エラー表示と復元を確認する
- [ ] 成功後のID、順序、件数が正式データと一致することを確認する
- [ ] 通常のServer Action版と操作完了までの体感を比較する

## 完了条件

- [ ] 3操作がサーバー応答前に仮反映される
- [ ] 成功時に正式データへ収束する
- [ ] 失敗時に不正な仮状態が残らない

## 学習後に説明できること
